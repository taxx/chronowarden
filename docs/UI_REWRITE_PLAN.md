Status: **feature-complete for v1** on branch `feat/ui-rewrite` (branched from
`feat/selfhost`). The API, database, backups and deployment stay as they are;
only the client is replaced. Remaining polish: Overview week/year views,

## Why

The Flutter web client renders to a canvas, which costs us: no real DOM/CSS
control, bolt-on accessibility (the semantics tree we had to enable for E2E),
awkward text/IME/clipboard/zoom behaviour, multi-MB CanvasKit payloads, no real
URLs/deep links, and a testing story (Playwright) that fights the framework. This
is a web-only product — no native targets — so a web-native stack is the right
trade.

## Hard constraint: crypto interoperability

The rewrite must read/write data produced by the current client. Port
`apps/web/lib/services/crypto_service.dart` **exactly**:

- **KEK:** PBKDF2-HMAC-SHA256, 310 000 iterations, 32-byte output (WebCrypto).
- **Wrap/encrypt:** AES-256-GCM, 12-byte nonce, 16-byte tag, stored as
  `base64(nonce ‖ ciphertext ‖ tag)` (WebCrypto emits `ciphertext ‖ tag`).
- **Recovery hash:** `base64(SHA-256(utf8(phrase)))`.
- **Recovery phrase:** **official BIP39** via `@scure/bip39` (English wordlist),
  replacing the Dart client's bespoke 2048-word list. Decision: an audited
  library beats maintaining a custom list, and there are only a handful of
  accounts.
  - **Migration:** a mnemonic only *encodes* the DEK, so the **DEK, envelope and
    passphrase are unchanged** — the phrase is simply different words. The new
    client derives the phrase from the DEK (on unlock and in Settings → Show
    recovery phrase) and rewrites `recovery_hash`. Users record the new phrase
    once; the maintainer coordinates this with the current accounts.
  - Old custom-wordlist phrases are retired; the client no longer decodes them.
  - The golden fixture's `recovery_phrase`/`recovery_hash_b64` fields are legacy
    (custom wordlist); the envelope/ciphertext fields are what prove data interop.
- **Client caches:** `localStorage['cw_dek']` (base64 32 bytes),
  `localStorage['cw_api_token']` (legacy bearer; dropped once cookies land).

Interoperability is proven with **golden fixtures generated by the Dart
implementation** (`apps/web/test/crypto_golden_test.dart` →
`apps/web-next/src/lib/__fixtures__/crypto-golden.json`). The TS implementation
must unwrap the wrapped DEK and decrypt the ciphertext byte-for-byte, and a real
restore of an existing backup is exercised end to end.

## The domain logic is the asset

The minute math is the heart of the app and is already unit-tested in Dart. Port
it to pure TypeScript **first**, with the tests, before any UI:

`work_config` (ISO weeks, reduced weeks), `time_log` (expected/overhead/lunch/
non-work, leave time, overtime), `format`, `notification_service`
(`evaluateLeaveAlert`), `transit_fetch_guard`, `csv` import/export, `pinned_journey`.

## Repository layout (transition)

```
apps/
  api/                unchanged Bun + Hono API
  web/                current Flutter client (kept working for beta testers)
  web-next/           the React rewrite (this branch)
packages/
  shared/             API DTO types shared by the API and the new client
```

At cutover the Flutter app is retired and `web-next` becomes `apps/web`. Until
then both build from the same repo and either can be served.

## API changes (small, backwards compatible)

- `POST /auth/login|setup|register` also sets an httpOnly `cw_session` cookie
  (SameSite=Lax, Secure in production), while still returning the bearer token
  for the Flutter client.
- `requireAuth` accepts the bearer token **or** the cookie.
- `GET /events` accepts the cookie (no token query param needed for the new
  client).
- `POST /auth/logout` clears the cookie.

## Phases

1. **Foundation** — scaffold, tooling, i18n, design tokens, crypto port + golden
   tests, domain port + tests, API client.
2. **Auth** — setup/first-admin, invite registration, login, passphrase unlock,
   recovery onboarding, cookie sessions, passphrase screen.
3. **Core day** — My Day (timers, lunch, non-work, flex, live leave time,
   notifications).
4. **History / Overview / Projection** — tables, calendars, charts.
5. **Settings** — work config, presets, transit, notifications, language,
   slider, flex, non-work, backup/restore, changelog, update prompt.
6. **Transit** — SL search, trips, pinned journey, back-off card.
7. **Admin** — users, invites, roles/status.
8. **PWA + polish** — installability, update prompt, accessibility.
9. **Cutover** — parity QA, swap clients, retire Flutter.

Each phase lands with Vitest/Testing Library coverage and Playwright E2E against
the real DOM (no semantics hacks).
