# Encryption Architecture — ChronoWarden

ChronoWarden is **zero-knowledge**: the server stores only AES-256-GCM
ciphertext and envelope metadata it cannot unwrap. This document describes the
design and the current client implementation.

> Design record. It also preserves the original rationale; the implementation
> today lives in the React client (`apps/web/src/lib/crypto.ts`).

## Why

Without client-side encryption, anyone with database or backup access can read
every row. The API scopes each query to its owner, but that does not protect data
at rest. Envelope encryption closes that gap: keys never leave the device.

## Key hierarchy

```
Passphrase ──PBKDF2(310k)──▶ Master Key (KEK)
                               │ AES-GCM wrap
                               ▼
                        Data Encryption Key (DEK)   (random 256-bit)
                               │ AES-GCM
                               ▼
                        Encrypted data (base64)
```

- The **DEK is random** and created once per account. It is wrapped by a KEK
  derived from the user's passphrase and stored in `user_settings.encrypted_dek`.
- Changing the passphrase only re-wraps the DEK; the ciphertext is untouched.
- The recovery phrase encodes the DEK directly, so a forgotten passphrase can be
  recovered without re-encrypting anything.

## Parameters & formats

| Step | Algorithm |
|------|-----------|
| KEK derivation | PBKDF2-HMAC-SHA256, **310 000** iterations, 16-byte salt, 32-byte key |
| DEK wrap / data | **AES-256-GCM**, 12-byte nonce, 16-byte tag |
| Stored form | `base64(nonce ‖ ciphertext ‖ tag)` |
| Recovery hash | `base64(SHA-256(utf8(phrase)))` |
| Recovery phrase | **BIP39**, 24 words (256-bit entropy + 8-bit checksum) |

WebCrypto emits `ciphertext ‖ tag`, so the client prepends the nonce and splits
on read.

## What is encrypted

- `time_logs.encrypted_data` — every workday (times, expected/overhead/lunch/
  non-work/flex/note).
- `travel_presets.encrypted_data` — the commute numbers (`name` stays plaintext
  for dropdowns).
- `user_settings.encrypted_data` — work config, flex, language, transit config,
  local preferences.

## What stays plaintext

- `user_id` (ownership scoping), `date` (server-side filtering), row
  `id`/`created_at`, and the preset `name`.

## Envelope columns (`user_settings`)

| Column | Meaning |
|--------|---------|
| `encrypted_dek` | wrapped DEK, `base64(nonce ‖ ct ‖ tag)` |
| `kek_salt` | PBKDF2 salt (base64) |
| `kek_iterations` | 310000 |
| `recovery_hash` | SHA-256 of the recovery phrase (base64) |

## Recovery phrase

- A 24-word BIP39 mnemonic encodes the DEK directly (`@scure/bip39`, official
  English wordlist).
- Its SHA-256 hash is stored in `recovery_hash` for verification, but the real
  check is decrypting the settings payload (robust across wordlists).
- Shown once after signup, and any time from Settings → Recovery phrase.

### Wordlist migration

The original client used a bespoke 2048-word list. The React client uses the
official BIP39 list. Because a phrase only encodes the DEK, **the DEK, envelope
and passphrase are unchanged** — only the words differ. On unlock (and when the
phrase is shown) the client re-derives the phrase from the DEK and rewrites
`recovery_hash`, so users simply note their new phrase once.

## Interoperability (proven)

`apps/web/src/lib/crypto.ts` is a byte-for-byte port of the original client's
crypto implementation. It is verified against golden fixtures generated by that
implementation (`apps/web/src/lib/__fixtures__/crypto-golden.json`):

- derive the KEK and unwrap the wrapped DEK → matches,
- decrypt a ciphertext produced by the old client → matches,
- BIP39 encode/decode round-trips and hashing is deterministic.

That means existing envelopes, ciphertext and passphrases keep working after the
client rewrite, and a real backup restore is exercised end to end in the
Playwright suite.

## Client implementation

| File | Purpose |
|------|---------|
| `apps/web/src/lib/crypto.ts` | PBKDF2, AES-256-GCM, wrap/unwrap, BIP39, base64, recovery hash |
| `apps/web/src/state/auth.ts` | DEK lifecycle, unlock, envelope detection, hash migration, DEK cache |
| `apps/web/src/services/time-logs.ts` | encrypt/decrypt time logs |
| `apps/web/src/services/settings.ts` | encrypt/decrypt settings payloads |
| `apps/web/src/services/travel-presets.ts` | encrypt/decrypt presets |
| `apps/web/src/components/BackupCard.tsx` | export/restore bundle |
| `apps/web/src/components/RecoveryPhraseCard.tsx` | show the recovery phrase |
| `apps/web/src/screens/RecoverScreen.tsx` | recover with the phrase + set a new passphrase |

The DEK is cached in `localStorage` (`cw_dek`) so a page refresh doesn't require
re-entering the passphrase; it is cleared on logout and after a restore.

## Threat model

- The server, its operator, and database backups see only ciphertext.
- `localStorage` holds the DEK and the session cookie is httpOnly; an XSS that
  runs in the app's origin could still read the DEK. Keep dependencies current.
- If the user loses **both** the passphrase and the recovery phrase, the data is
  irrecoverable.
