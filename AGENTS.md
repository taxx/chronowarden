# Agent Context: ChronoWarden Coding Harness

You are an expert Flutter/Dart + TypeScript developer acting as a dedicated
pair-programmer for **ChronoWarden**, a personal time-tracking and
overtime-protection app. The stack is 100 % self-hosted: a Flutter web client
talks to a Bun/Hono API backed by PostgreSQL, all run with Docker Compose.

## Core Directives

1. **KISS Principle:** Prioritize clean, minimal, readable, and highly
   maintainable code. Avoid over-engineering, unnecessary abstractions, or
   redundant boilerplate.
2. **State Management (client):** Use Flutter's native `ChangeNotifier` or
   simple state-lifting. Do not introduce heavy third-party architecture
   frameworks unless explicitly requested.
3. **Time & Duration Representation:** All time durations (expected work time,
   overhead buffers, overtime net balances) MUST be handled and stored as an
   `int` representing total minutes in both backend and domain models.
   Conversion to `Duration` objects or formatted strings (`HH:mm`) belongs
   strictly in the UI/presentation layer.
4. **Data Privacy & Isolation:** Every user-data query is scoped to the
   authenticated user. There is no RLS: the API is the only client of the
   database and enforces ownership in the route layer. Never accept a
   `user_id` from the client for scoping.
5. **Validation:** `flutter analyze` (in `apps/web`) and
   `bunx tsc --noEmit` (in `apps/api`) must be clean.
6. **Tests:** Use tests and mocks where applicable to ensure you don't break
   things and make sure new features work. `flutter test` and `bun test` must
   pass.
7. **Deploy as part of the routine:** Every completed code change (fix or
   feature) MUST be deployed as part of the same working session, unless the
   user explicitly says not to. After committing and pushing, run the SSH
   rebuild + verification steps in "Release to production" below.
8. **Localization:** All user-facing text goes through `context.t('English
   text')` (or `strings.translate(...)` in pure helpers with no
   `BuildContext`). Add the Swedish entry to
   `apps/web/lib/l10n/app_strings_sv.dart` **in the same commit**, or
   `test/app_strings_test.dart` fails. See the "Localization (i18n)" section.
9. **Generated metadata:** `CHANGELOG.md`, `build_info.json`, and
   `web/version.json` are generated by `apps/web/tool/*.sh` (and regenerated
   during the Docker build). Never hand-edit them — run the generators before
   committing (see "Release to production → Step 1").

## Architecture Overview

```
                        https://chronowarden.slumpen.com  (host reverse proxy, TLS)
                                        │
                              ┌─────────▼──────────┐
                              │  proxy (nginx)     │   8981:80
                              │  /api/* → api      │
                              │  /*     → web      │
                              └───┬────────────┬───┘
                                  │            │
                    ┌─────────────▼──┐   ┌─────▼──────────────┐
                    │  web (nginx)   │   │  api (Bun + Hono)  │
                    │  Flutter build │   │  REST + SSE + SL   │
                    └────────────────┘   └─────┬──────────────┘
                                               │
                                        ┌──────▼───────┐
                                        │ postgres:18  │  (volume data/postgres)
                                        └──────┬───────┘
                                               │
                                        ┌──────▼───────┐
                                        │  backup      │  pg_dump + retention
                                        └──────────────┘
```

- **Same origin** for app and API (`/api/*`) → no CORS and no API URL baked
  into the JS bundle.
- All writes go through the API, so cross-device sync uses **SSE** (the API
  publishes an event per write) instead of Postgres logical replication.
- The SL Journey Planner proxy + response slimming live in the API
  (`POST /api/v1/sl/proxy`), not a separate service.
- The database is not published on the host; only the API reaches it.
- Zero-knowledge: the server only ever stores AES-256-GCM ciphertext plus the
  envelope metadata it cannot unwrap.

## Authentication & Multi-User

ChronoWarden uses invite-only registration with local accounts. Admins manage
users but cannot read their data — each user operates on an isolated "island".
See [`docs/AUTH.md`](docs/AUTH.md) for the full reference.

### Roles & statuses (`users` table)

| Role | Status | Meaning |
|------|--------|---------|
| `admin` | `approved` | Manage users/invites. Sees only own data. |
| `user` | `approved` | Regular user (invite registration is auto-approved). |
| `user` | `pending` | Exists but not approved (reserved; invite flow grants immediately). |
| `user` | `rejected` | Disabled; login is refused. |

### First admin (empty database)

1. The client calls `GET /state`; `has_users == false` shows "Create Admin".
2. `POST /auth/setup` creates the account as `admin` / `approved` and returns a
   session token. It only succeeds while the database is empty.

### Regular users (invite-only)

1. An admin creates an invite (`POST /admin/invites`) for a specific email.
   Only the SHA-256 hash is stored; the raw token is returned **once** so the
   admin can share it out-of-band. There is no email delivery.
2. The user enters the token at signup; `POST /invites/validate` confirms it
   and returns the bound email (the client prefills it).
3. `POST /auth/register` creates the account with the invite's role and marks
   the invite used. Invites are single-use and expire (default 14 days, max 90).

### Credentials & sessions

- Passwords are hashed with **argon2id** (`Bun.password`, 19 MiB / 2
  iterations). Minimum length 10 characters.
- Sessions are opaque 256-bit tokens. Only their SHA-256 hash is stored, in
  `sessions`. The TTL is sliding (`SESSION_TTL_DAYS`, default 30) and the token
  is revoked on logout.
- The client caches the token in `localStorage` (`cw_api_token`) via
  `ApiClient`.

### Password resets (no email)

Password resets are admin-assisted: an admin can issue a new temporary
password out-of-band. The **encryption passphrase is separate and never
changes**; data recovery uses the recovery phrase.

## Encryption Architecture

ChronoWarden uses **envelope encryption** (zero-knowledge) to protect user
data. The backend change did not touch this — the server is still blind.

### Key hierarchy

```
Passphrase → PBKDF2(310k) → Master Key (KEK)
  └─ AES-GCM wrap ──→ Data Encryption Key (DEK)
                        └─ AES-GCM encrypt ──→ Encrypted data
```

### What's encrypted

- All `time_logs` rows → `encrypted_data` (AES-256-GCM)
- All `travel_presets` rows → `encrypted_data`
- `user_settings` → `encrypted_data` (work config, flex, language, transit)
- `user_settings` envelope columns: `encrypted_dek`, `kek_salt`,
  `kek_iterations`, `recovery_hash`

### What stays plaintext

- `user_id` (ownership scoping), `date` (server-side filtering), `time_logs`
  and `travel_presets` `id`/`created_at`, the preset `name` (dropdowns)

### Key files

| File | Purpose |
|------|---------|
| `apps/web/lib/services/crypto_service.dart` | PBKDF2, AES-256-GCM, key wrap, BIP39 mnemonic, localStorage cache |
| `apps/web/lib/services/auth_service.dart` | session + DEK lifecycle, passphrase unlock, envelope detection |
| `apps/web/lib/services/migration_service.dart` | legacy plaintext → encryption (effectively retired) |
| `apps/web/lib/services/backup_service.dart` | export/restore bundle |
| `apps/web/lib/screens/passphrase_screen.dart` | passphrase entry on new devices |
| `apps/web/lib/screens/about_encryption_screen.dart` | encryption explainer (`EncryptionInfoContent`) |

### Recovery phrase

- A 24-word BIP39-style mnemonic encodes the DEK directly.
- Its SHA-256 hash lives in `user_settings.recovery_hash` for verification.
- Shown once during signup/restore; accessible from Settings → Encryption.

### Critical warning (displayed in UI)

> If you lose both your encryption passphrase AND your recovery phrase,
> your data is gone forever. No one — not even the app administrator —
> can recover it.

## Backup & Restore (data portability)

Users can move all their data between instances:
**Settings → Backup & Restore**.

- `GET /export` returns a JSON bundle:
  `{ format, version, exported_at, user, envelope, settings, time_logs,
  travel_presets }` where the envelope carries `encrypted_dek`, `kek_salt`,
  `kek_iterations`, `recovery_hash`, and every row is ciphertext.
- `POST /import` replaces the account's envelope + rows atomically.
- The **envelope must travel with the data**: the DEK is random, so a fresh
  signup on the target instance would otherwise derive a different key. After
  restore the client drops any in-memory DEK and prompts for the *backup's*
  passphrase (`AuthService.onBackupRestored()` → passphrase screen).
- CSV export/import (time logs only) remains for spreadsheet workflows.

## Cross-Device Realtime Sync

The API publishes changes over Server-Sent Events; there is no third-party
realtime service.

### How it works

1. `AppState._subscribeRealtime()` opens
   `GET /api/v1/events?token=<session>` via `RealtimeService` (browser
   `EventSource`, behind the `web_browser` conditional-import bridge).
2. On any `time_logs` write the API publishes `{ table, type, row }` to that
   user's open streams (`apps/api/src/events.ts`).
3. `AppState._onRealtimeEvent()` re-fetches today's log and the full list so
   My Day, Overview and History update without a page reload.
4. The subscription is stopped on sign out (`AppState.onSignOut()`).

The hub is in-process, so it assumes a single API container. `EventSource`
reconnects automatically; `MyDayTab` also re-checks on app resume.

Key files: `apps/web/lib/services/realtime_service.dart`,
`apps/web/lib/app_state.dart`, `apps/api/src/events.ts`,
`apps/web/lib/utils/web_browser*.dart`.

## Real-Time Transit Integration (SL Journey Planner)

```
Flutter Web
  └─ ApiClient.post('/sl/proxy', { path })
       └─ API route (Bun) — slims the ~220 KB /v2/trips response to ~2 KB
            └─ fetch('https://journeyplanner.integration.sl.se/v2/...')
                 └─ Slimmed JSON (departure/arrival, legs with line,
                     platform, occupancy, delay) back to Flutter
```

### Why slimming (and why the proxy stays)

Slimming keeps the payload small. The proxy is now the API itself: being
same-origin removes the CORS reason, but the server also holds an optional
`SL_API_KEY`, caches identical queries for 30 s, and only allows `/v2/` paths.

### Smart direction logic

- Morning (before 11:00): home → work
- Afternoon (11:00+): work → home

### Walk-offset query time

The query time is offset by the walking time so the API returns journeys that
depart after the user has walked to the station.

### Station autocomplete

`/v2/stop-finder`, 300 ms debounce, no caching. Returns Journey Planner global
IDs (e.g. `9091001001009638`).

### Transit config storage

Stored encrypted in `user_settings.encrypted_data` under `transit_config`:
`enabled`, `work_stop_id`/`work_stop_name`, `home_stop_id`/`home_stop_name`,
`walk_home_minutes`/`walk_work_minutes`.

### Transit tab visibility

The Transit destination only appears once `enabled` is true.

### My Day transit card visibility

Context-sensitive — appears only when the applicable travel preset uses transit:

- **Active/completed day** — matched to a preset by its four per-direction
  commute values (`TravelPreset.matchesLog` / `findPresetForLog`).
- **No day yet** — it is planning, so shown whenever the user commutes by
  transit at all (`shouldShowTransitPlanningForPresets`).
- **Unknown selection** — shown, so transit users are never cut off.
- **Weekends** — pre-start card hidden unless the show-weekends setting is on;
  an active day always shows it.

`PreferencesService.init()` runs in `main()` so show-weekends is loaded before
the first frame.

### Failure back-off & rate limiting

The app must never hammer SL:

- **`TransitFetchGuard`** (`apps/web/lib/services/transit_fetch_guard.dart`) —
  pure, clock-injected retry policy: exponential back-off with equal jitter
  (base 15 s → cap 15 min), honoring `Retry-After`. A non-retryable status
  (400/401/403) or `maxFailures` consecutive failures gives up until an
  explicit `TransitService.retryNow()`.
- **`TransitService.fetchJourneys()`** checks the guard before the network and
  returns stale cache while backing off. Failures become guard state inside
  `_runFetch`, which never rejects (coalesced callers can't see a throw).
- **UI never fetches from `build()`.** `MyDayTab._maybeRefreshTransit()` runs
  from its 1 s ticker and on resume; cache TTL/guard make it a cheap no-op.
- **User-visible state:** `TransitUnavailableCard` shows a retry countdown or
  the give-up message plus **Try again**.
- **Server hardening:** the API caches paths for 30 s; the client back-off is
  the real protection.

Unit tests: `apps/web/test/transit_fetch_guard_test.dart`.

Key files: `apps/web/lib/models/{transit_config,journey_info,station_info}.dart`,
`apps/web/lib/services/{transit_service,transit_fetch_guard}.dart`,
`apps/web/lib/widgets/{transit_unavailable_card,station_picker}.dart`,
`apps/web/lib/screens/transit_screen.dart`, `apps/api/src/sl.ts`.

### Pinned (committed) journey

The SL API returns at most 3 trips; a committed train can slide out of the
window. Pinning keeps it visible.

- **Matching** by scheduled departure time-of-day + line + route (so delays
  don't make it slide).
- **Storage** in `localStorage` (per-device, not encrypted).
- **Auto-expire** when departure has passed or the day ends.
- **Behavior** — pinned card renders at top with a Locked badge; uses live data
  when present, otherwise a synthetic card. Cleared when stations change.

Files: `apps/web/lib/models/pinned_journey.dart`,
`apps/web/lib/services/pinned_journey_store.dart`.

## Non-work time (errands)

A day can contain **non-work time** (errands, appointments). It behaves like
lunch: not-working time, excluded from overtime.

- **Model:** `TimeLog.nonWorkMinutes` (int, inside `encrypted_data` as
  `non_work_minutes`, default 0). `TimeLog.nonWorkStartedAt` mirrors
  `lunchStartedAt` for live-timer sync. No SQL migration needed.
- **Calculator:** `leaveTime` / `calculateLeaveTime()` add non-work minutes and
  `calculateOvertimeMinutes()` subtracts them.
- **Live timer:** `AppState.startNonWork() / stopNonWork() /
  updateNonWorkMinutes()` and `effectiveLeaveTime()` extend the projected leave
  time by whichever is larger of stored vs. elapsed.
- **UI:** the shared `BreakTimerSection` renders lunch and non-work.
- **Feature toggle:** `AppState.nonWorkEnabled` (default true), persisted via
  `UserSettingsService.getNonWorkEnabled/setNonWorkEnabled`.
- **CSV:** `non_work_minutes` is the **last** export column so older CSVs still
  import.

## Leave-time notifications

While a day is active the app watches the projected leave time and alerts when
close to leaving, then again if overrunning.

### Two phases

- **Wrap-up** — once `remaining <= notification_threshold_minutes` (default 30):
  `⏰ <time> left — wrap up and head out!`
- **Overtime** — once leave time passes (up to 60 min):
  `🚨 <n> min past your time — finish up and stop the day!`

### Snooze & dismiss

- **Snooze** (default 10 min, configurable 1–30) re-arms the alert.
- **Dismiss** (✕) suppresses alerts for the rest of the day.
- State and settings persist to `SharedPreferences`; a delivered-but-undecided
  alert is restored silently after a reload.

### Delivery

1. **In-app banner** (`AlertBanner`, hosted by `MainShell`).
2. **OS notification** (`showOsNotification()`, Notification API), when granted.
3. **Beep + vibration** (Web Audio, `navigator.vibrate`).

### Audio lifecycle

Browsers suspend `AudioContext` until a gesture:

- A single shared `window._cwAudioCtx` is reused for all beeps.
- `NotificationService.init()` registers the JS bridge immediately.
- `NotificationService.primeAudio()` is called from the first pointer-down
  (`MaterialApp.builder` → `Listener` in `main.dart`) and the Sound toggle.

### Catch-up on return

`MyDayTab` is a `WidgetsBindingObserver` and re-runs `check()` on resume.

### Diagnostics

Settings → Notifications shows permission, audio state and vibration support
(`NotificationService.permissionStatus/audioStatus/vibrationSupported`).

### Robustness

- Timing decisions live in the pure `evaluateLeaveAlert()` in
  `apps/web/lib/services/notification_service.dart` (unit-tested).
- The projected leave time accounts for an overrunning lunch timer.

## Changelog / What's New

```
apps/web/tool/generate_changelog.sh → apps/web/CHANGELOG.md (committed asset)
   → ChangelogService.load() → parseChangelog() → ChangelogScreen
```

- Run it as part of the release routine (before `git commit`).

**What's New**.

### Static asset caching (nginx)

The web image's nginx sends `Cache-Control: no-cache, no-store,
must-revalidate` for every text asset that changes between builds:
`location ~ \.(js|dart|html|json|md|sql|txt|xml)$`. Add new extensions when you
ship new build-generated text assets.

### Generated file permissions

`tool/*.sh` `chmod 644` their output so the non-root nginx worker can serve it.

## Version Check / Update Prompt

Long-lived tabs keep running the JS they loaded, so the app detects newer
deployments and offers a reload.

```
apps/web/tool/generate_build_info.sh
   ├─ build_info.json   → Flutter asset (the running app's own commit)
   └─ web/version.json  → served by nginx at /version.json (server commit)
                ↓
UpdateService polls /version.json?t=<ts> → isUpdateAvailable()
                ↓
UpdateBanner (MainShell) → "Reload" → web_browser.reloadPage()
```

- Both files contain `{version, commit, built_at}` from the same commit; the
  **commit id** is the comparison key.
- Polls every 5 minutes and immediately when the tab becomes visible.
- Prompts only when both commits are known (not `dev`) and differ.
- **Dismiss** records the server commit; reappears for the next deploy.
- **Reload** calls `window.location.reload()`.

Key files: `apps/web/tool/generate_build_info.sh`,
`apps/web/lib/models/build_info.dart`,
`apps/web/lib/services/update_service.dart`,
`apps/web/lib/widgets/update_banner.dart`,
`apps/web/lib/utils/web_browser*.dart`, `apps/web/test/build_info_test.dart`.

`apps/web/test/app_strings_test.dart` scans `lib/` for `context.t('…')` and

Add a catalog + a case in `AppStrings.forLocale`, add the code to
`LocaleService.supportedLanguages` and `MaterialApp.supportedLocales`, and
extend the delegate.

## iOS Safari Paste Compatibility

iOS Safari doesn't fire paste events to canvas-rendered TextFields. A
`PasteButton` reads the Flutter `Clipboard` directly.

Used on: PassphraseScreen recovery dialog; LoginScreen passphrase; SignupScreen
passphrase + confirm.

```dart
TextField(controller: ctrl, decoration: InputDecoration(suffixIcon: PasteButton(controller: ctrl)))
```
